# Демо к лекции 2

Эталон — одноразовые **Ubuntu Server 26.04 LTS VM**, Bash, локаль вывода C.
Сценарии 01–04, 07–13 изменяют состояние VM; 05 и 06 работают без root и не меняют учётные записи.
Нумерация задаёт учебный каталог, а не зависимости: независимые демо можно запускать отдельно.
Сценарии 12–13 относятся к подразделу 2.3 лекции (идентификаторы процесса) и получили
следующие свободные номера, чтобы не перенумеровывать готовые захваты.

## Подготовка

Создайте снимок VM, обеспечьте доступ к её консоли. Не используйте рабочую машину,
общую серверную VM или VM с настоящими секретами. Выполняйте только один сценарий
и не меняйте параллельно пользователей, группы и PAM. Локальный flock предотвращает
одновременный запуск этих сценариев, но не блокирует действия других администраторов.

Установка зависимостей на локальной учебной VM:

~~~bash
sudo apt-get update
sudo apt-get install sudo passwd login util-linux openssl python3 shellcheck \
  wtmpdb lastlog2 libpam-wtmpdb libpam-lastlog2 procps gcc
~~~

Рабочий каталог — этот каталог assets/demos. Запуск через Bash не требует executable bit:

~~~bash
bash 01-passwd-uid-zero.sh --help
sudo env OSSEC_DEMO_VM=1 bash 01-passwd-uid-zero.sh
bash 05-password-hashes.sh
bash 06-timing-attack.sh
~~~

OSSEC_DEMO_VM=1 — явное подтверждение оператора, **не техническое доказательство изоляции**.
Скрипты проверяют root, версию ОС, зависимости и конфликты создаваемых записей.
Интерактивные сценарии запускайте из терминала; не передавайте их через pipe.
Пароли из слайдов публичны и предназначены только для временных учебных записей.

## Сценарии, результат и очистка

| Файл | Действия / критерий успеха | Очистка |
|---|---|---|
| 01-passwd-uid-zero.sh | Новый процесс временного пользователя получает UID 0 | UID восстанавливается через vipw, затем userdel |
| 02-group-membership.sh | id/groups согласуются с passwd/group | Временный пользователь и членство удаляются |
| 03-group-password-sudo.sh | gpasswd задаёт пароль; неучастник выполняет newgrp sudo; id -gn → sudo | Восстанавливается исходный gshadow, удаляется пользователь |
| 04-shadow-password-policy.sh | passwd меняет verifier и last-change; chage показывает новые вычисленные даты | Временная запись удаляется |
| 05-password-hashes.sh | По два хэша -1/-5/-6, одинаковая соль даёт IDENTICAL | Не требуется |
| 06-timing-attack.sh | Восстановлен синтетический секрет cabdab; показан compare_digest | Не требуется |
| 07-user-lifecycle.sh | Создание, изменение, копирование skel, удаление | Временные home и пользователь удаляются |
| 08-login-accounting.sh | Настоящий login; who/w в сессии, last/lastlog после неё | Пользователь удаляется, журналы сохраняются |
| 09-su-sudo.sh | Сначала пароль sudo, затем -k -n id без запроса | Удаляется только /etc/sudoers.d/ossec-demo и пользователь |
| 10-ldap-server.sh | TLS, каталог, LDAP user, порт 1389 | Сервер останавливается, временные база/ключи удаляются |
| 11-ldap-client.sh | getent/id, LDAP bind, login с паролем LDAP | Остановка SSSD, восстановление NSS/PAM, удаление demo config/CA/cache |
| 12-process-credentials.sh | /proc/PID/status и ps: четыре UID; у setuid-passwd ruid≠euid=0 | Фоновые sleep/passwd завершаются, пользователь удаляется |
| 13-uid-inheritance.sh | setuid-утилита idprobe: fork наследует suid, execve сохраняет euid, bash сбрасывает euid без -p, setuid-бит скриптов игнорируется | Удаляются /usr/local/bin/ossec-idprobe, ossec-suid-script и пользователь |

Сценарии выводят исполняемые команды и их реальный результат. В слайдах дан
**ожидаемый иллюстративный вывод**, не протокол проверки на вашей VM.
UID/GID, даты, порядок групп, дополнительные группы, хэши и локализованные приглашения могут отличаться.

### Интерактивные действия

- **03**: задайте пароль группы. В запущенном Bash выполните newgrp sudo,
  введите именно пароль группы, затем id -g и id -gn. Дважды exit:
  сначала из newgrp-shell, затем из исходного shell.
- **04**: задайте новый пароль через passwd. Скрипт заранее выставляет last-change
  на десять дней назад, чтобы смена в тот же календарный день была наглядна.
- **08**: задайте пароль, войдите как ossec-demo, выполните id, who, w, exit.
  Для lastb сначала сделайте одну неудачную попытку. Наличие записей зависит от
  настроенного login/PAM: отсутствие вывода само по себе не ошибка парсинга.
- **09**: задайте пароль ossec-demo и введите его при запросе sudo. Второй вызов
  sudo -k -n должен пройти без запроса; правило разрешает только /usr/bin/id.

Не закрывайте VM принудительно во время UID=0-демо. EXIT/INT/TERM запускают cleanup,
но SIGKILL, отключение питания и сбой диска не позволяют гарантировать откат.
Если восстановление UID не удалось, не запускайте userdel для UID 0: верните снимок VM.
Утилиты могут оставлять резервные файлы passwd-/shadow- и журнальные записи.
Удаление пользователя не удаляет историю входов, lastlog или файлы по всей системе.
**Полное восстановление исходного состояния — возврат снимка**.

## LDAP: сервер и клиент

Две VM в частной сети: пример server 192.168.56.10, client 192.168.56.11.
Разрешите TCP 1389 от клиента к серверу в правилах вашей учебной сети.
Интернет требуется для установки пакетов; открывать LDAP в публичную сеть не нужно.
Используйте консоль VM, чтобы изменение PAM не лишило доступа к управлению.

На сервере:

~~~bash
sudo apt-get update
sudo apt-get install slapd ldap-utils openssl python3
sudo env OSSEC_DEMO_VM=1 LDAP_SERVER_IP=192.168.56.10 \
  bash 10-ldap-server.sh
~~~

Диалог установки slapd относится к пакетному серверу; сценарий запускает
**отдельный экземпляр** на 1389 с временным slapd.conf и базой, не меняя cn=config
пакетной службы. Введите разные временные пароли администратора и ldapstudent
(минимум 12 символов). Скрипт требует TLS для simple bind; хэши LDAP создаёт slappasswd.
Временные конфигурация/ключи находятся в /etc/ldap/ossec-demo.*, база — в
/var/lib/ldap/ossec-demo.*, PID — в /run/slapd/: это пути штатного AppArmor-профиля.
Профиль не отключается; эти временные данные удаляются при выходе.

Терминал покажет публичный PEM-сертификат и SHA-256 fingerprint.
Сохраните **только блок BEGIN CERTIFICATE…END CERTIFICATE** на клиенте как
/tmp/ossec-ldap-ca.crt. Сверьте на клиенте:

~~~bash
openssl x509 -in /tmp/ossec-ldap-ca.crt -noout -fingerprint -sha256
~~~

Не копируйте tls.key, admin-secret, user-secret или весь временный каталог.
Сервер остаётся работающим до нажатия Enter в его терминале.

На свежем клиенте:

~~~bash
sudo apt-get update
sudo apt-get install sssd-ldap sssd-tools libnss-sss libpam-sss ldap-utils
sudo systemctl stop sssd
sudo env OSSEC_DEMO_VM=1 LDAP_SERVER_IP=192.168.56.10 \
  LDAP_CA_FILE=/tmp/ossec-ldap-ca.crt bash 11-ldap-client.sh
~~~

Клиент откажется перезаписывать существующий sssd.conf, demo CA или home,
использовать занятый UID/GID 20000 либо менять активный SSSD.
Отдельная VM клиента необходима: серверный и клиентский сценарии на одной машине
конфликтуют по общей блокировке.

Ожидаемая цепочка проверки:

1. sssctl config-check проходит.
2. NSS: passwd/group имеют files systemd sss, shadow остаётся files.
3. getent passwd ldapstudent и id ldapstudent дают UID/GID 20000 без локальной записи.
4. ldapwhoami -ZZ с паролем ldapstudent возвращает DN.
5. В login введите ldapstudent и его пароль; id -u → 20000, pwd → /home/ldapstudent.
6. Выполните exit, затем Enter для cleanup клиента, после этого Enter на сервере.

Удалённый хэш не появляется в локальном shadow: NSS получает атрибуты,
а pam_sss проверяет пароль через SSSD. TLS обязателен и для идентификационных
запросов (ldap_id_use_start_tls), сертификат проверяется (demand), кэш паролей отключён.
access_provider=permit — упрощение только для этого учебного каталога.

Клиент восстанавливает исходные common-* и nsswitch.conf. Установленные пакеты,
метаданные pam-auth-update, home ldapstudent и журналы сохраняются: для повторения
используйте исходный снимок. Копию сертификата /tmp/ossec-ldap-ca.crt удаляет оператор.
Диагностика: journalctl -u sssd, /var/log/sssd/, sssctl config-check,
ldapwhoami -ZZ; не отключайте проверку сертификата ради обхода ошибки.

## Проверка материалов

~~~bash
for file in ./*.sh lib/common.sh; do bash -n "$file" || exit; done
shellcheck -x ./*.sh lib/common.sh
for file in ./*.sh; do bash "$file" --help || exit; done
bash 05-password-hashes.sh
bash 06-timing-attack.sh
~~~

Демо 05/06 можно проверять локально. Все остальные — на снимках Ubuntu 26.04.
После локальных демо убедитесь, что getent passwd ossec-demo ничего не возвращает,
дополнительных UID 0 нет, visudo -c проходит и demo-фрагмент sudoers отсутствует.
После LDAP: восстановлены исходные NSS/PAM, временная служба и порт 1389 закрыты.

Источники и форматы структур приведены в конце slides.md. Структура service_user
отмечена как glibc 2.31: в glibc 2.39 (Ubuntu 24.04) и новее такой структуры уже нет.

### Что проверено при подготовке

- Slidev production build; 55 непустых слайдов, первая страница — cover.
- Все слайды просмотрены автоматизированным Chromium-проходом с проверкой границ
  текста/таблиц/кода; дополнительно просмотрены снимки плотных слайдов.
- Bash syntax, --help и ShellCheck; реальные вычисления 05 и 06.
- В одноразовом Ubuntu-контейнере (проверено на 24.04): 01–04, 07–09, их интерактивные запросы,
  возврат UID, удаление временной записи и валидация sudoers.
- В двух изолированных Ubuntu-контейнерах: 10/11, TLS, LDAP bind, NSS lookup,
  парольный PAM login с UID 20000, создание home, побайтовое восстановление NSS/PAM.

Ограничения проверки: systemd не был PID 1 в тестовом контейнере, поэтому тестовый
адаптер запускал настоящий SSSD напрямую; штатные systemd units и применение
AppArmor-профиля необходимо проверить на VM. В минимальном контейнере login
прошёл, но who/last не показали сессию, lastlog дал Never logged in.
Полноценный учёт входов демо 08 следует проверить на VM с getty и журналами.
Вывод на слайдах остаётся иллюстративным, а не заявлением о полном VM-прогоне.

# Исчерпание ресурсов — угроза доступности, а не доступа

Механизмы разграничения доступа (лекции 2–4) отвечают на вопрос «*кому
разрешено* обращаться к объекту». Они не ограничивают, *сколько* ресурсов
вправе потребить уже допущенный к работе процесс, поэтому против угроз
**доступности** они неприменимы.

<div class="grid grid-cols-2 gap-3 mt-4">
<div class="p-3 border-l-4 border-red-500 bg-red-500/10">
<b>Истощение памяти</b><br/>
один процесс исчерпывает оперативную память, вынуждая ядро завершать
чужие процессы (OOM)
</div>
<div class="p-3 border-l-4 border-red-500 bg-red-500/10">
<b>Перепроизводство процессов</b><br/>
неограниченное ветвление (<i>fork bomb</i>) исчерпывает таблицу процессов
и процессорное время
</div>
<div class="p-3 border-l-4 border-red-500 bg-red-500/10">
<b>Исчерпание дескрипторов</b><br/>
процесс открывает файлы и сокеты до предела, и система теряет способность
принимать новые соединения
</div>
<div class="p-3 border-l-4 border-red-500 bg-red-500/10">
<b>Неограниченный рост файлов</b><br/>
запись «мусорных» данных заполняет файловую систему и останавливает
зависящие от неё службы
</div>
</div>

<div class="mt-4 p-2 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
Задача раздела — <b>разграничение ресурсов</b>: распределение конечных
ресурсов машины (процессорное время, память, дескрипторы, число процессов)
между процессами и пользователями так, чтобы ни один из них не нарушил
работу системы в целом.
</div>

# Два уровня разграничения ресурсов

Linux предоставляет два взаимодополняющих механизма; они различаются
единицей, к которой применяется ограничение, и моделью распределения.

<div class="t-table mt-4">

| Свойство | Лимиты ресурсов (`ulimit`) | Группы управления (`cgroup2`) |
|---|---|---|
| Единица ограничения | процесс и его потомки; пользователь (через PAM) | произвольная группа процессов (иерархия) |
| Что ограничивает | предел на **каждый** процесс по отдельности | **совокупное** потребление всех процессов группы |
| Модель | фиксированный верхний предел (мягкий / жёсткий) | веса, лимиты, защита, бронирование |
| Интерфейс | `getrlimit`/`setrlimit`, команда оболочки, `limits.conf` | псевдо-ФС `/sys/fs/cgroup` |
| Появление | исторический механизм Unix (RLIMIT) | ядро Linux, 2008 (v1) / 2016 (v2) |

</div>

<div class="mt-4 p-3 border-l-4 border-teal-500 bg-teal-500/10">
Лимиты ограничивают <b>отдельный процесс</b>, но не его группу: сто
процессов по 100 МБ обойдут лимит на процесс и исчерпают память совместно.
Этот недостаток устраняет <code>cgroup2</code>, ограничивающий
<b>суммарное</b> потребление группы. Раздел 2 посвящён лимитам, раздел 3 —
группам управления.
</div>

# Лимиты ресурсов ограничивают процесс и пользователя

Механизм лимитов ресурсов (*resource limits*, `RLIMIT`) задаёт верхний
предел потребления отдельного ресурса процессом. Ядро хранит пределы в
структуре процесса и проверяет их при каждом запросе ресурса.

<div class="grid grid-cols-2 gap-5 mt-3">
<div>

**Назначение механизма:**

1. поддержка **стабильности системы** — отказ одного процесса не
   распространяется на остальные;
2. **честное распределение** конечных ресурсов между пользователями;
3. **контроль администратора** над поведением приложений;
4. ограничение ресурсов при **тестировании** приложений.

</div>
<div>

**Решаемые проблемы доступности:**

- истощение памяти и адресного пространства;
- перепроизводство процессов (*fork bomb*);
- исчерпание файловых дескрипторов;
- чрезмерные дампы памяти (*core*);
- бесконтрольное использование CPU;
- неограниченный рост размера файла.

</div>
</div>

<div class="mt-3 p-2 border-l-4 border-amber-500 bg-amber-500/10 text-xs">
Лимит действует на <b>процесс</b>, а не на пользователя напрямую: проекция
на пользователя достигается применением лимита ко всем процессам его
сессии при входе — это делает <Man p="pam_limits(8)" /> (раздел 2.3).
</div>

<Refs ids="kerrisk-tlpi man-getrlimit" />

# Лимиты покрывают память, процессор, процессы и файлы

Команда `ulimit` оболочки `bash` управляет пределами текущего процесса по
аргументу-ключу; ниже — основные из ресурсов (<Man p="bash(1)" />,
<Man p="getrlimit(2)" />).

<div class="grid grid-cols-2 gap-x-6 text-xs mt-2">
<div class="t-table">

| Ключ | Ресурс | Предел |
|:---:|---|---|
| `-v` | `as` | адресное пространство (КБ) |
| `-m` | `rss` | резидентный набор (КБ) |
| `-d` | `data` | сегмент данных (КБ) |
| `-s` | `stack` | размер стека (КБ) |
| `-c` | `core` | размер core-файла (КБ) |
| `-l` | `memlock` | заблокированная память (КБ) |

</div>
<div class="t-table">

| Ключ | Ресурс | Предел |
|:---:|---|---|
| `-t` | `cpu` | процессорное время (с) |
| `-u` | `nproc` | число процессов пользователя |
| `-n` | `nofile` | число открытых файлов |

действующее ограничение, и **жёсткий лимит** (*hard limit*) — потолок, выше
которого мягкий поднять нельзя.

# Лимиты задаются из четырёх источников

<div class="grid grid-cols-2 gap-5 mt-2">
<div>

Значения пределов процесс получает из одного из источников:

1. **значения ядра по умолчанию** — наследуются от `init`;
2. **команда оболочки** `ulimit` — для текущей сессии;
3. **PAM и `/etc/security/limits.conf`** — при входе в систему;
4. **программно** — вызов `setrlimit()` в коде приложения.

Лимит наследуется при `fork(2)` и сохраняется при `execve(2)`, поэтому
значение, установленное процессу, действует на всё его поддерево.

</div>
<div>

**Проверка в ядре.** При каждом запросе ресурса ядро сравнивает
совокупное потребление с мягким лимитом:

<TerminalCapture content="if (usage + request > rlimit[RESOURCE].rlim_cur)
    return -EPERM;" title="ядро: проверка лимита" fontSize="0.6rem" :colorize="false" />

<div class="mt-2 p-2 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
Превышение не «замечается постфактум»: запрос, нарушающий лимит,
<b>отклоняется</b> кодом ошибки (<code>EPERM</code>, <code>EMFILE</code>,
<code>ENOMEM</code>) либо вызывает сигнал (<code>SIGXFSZ</code>,
<code>SIGXCPU</code>).
</div>

</div>
</div>

<div class="mt-2 p-2 border-l-4 border-amber-500 bg-amber-500/10 text-xs">
Лимиты, заданные командой <code>ulimit</code>, действуют <b>до завершения
сессии</b>. Постоянная настройка достигается записью в <code>limits.conf</code>
или в стартовые файлы оболочки (<code>~/.bashrc</code>).
</div>

Четыре источника значений лимита и правило наследования (fork сохраняет,

ядра показывает механику: проверка предварительная (usage+request против
rlim_cur), нарушающий запрос отклоняется, а не откатывается. Способ отказа
зависит от ресурса: системный вызов возвращает ошибку (EMFILE для nofile,
ENOMEM для as) либо ядро шлёт сигнал (SIGXFSZ при превышении fsize, SIGXCPU
при cpu). Амбер-блок: область действия ulimit — сессия; постоянство — через
limits.conf или bashrc.
-->

# cgroup: учёт и изоляция ресурсов на уровне группы процессов

**Группы управления** (*control groups*, `cgroup`) — механизм ядра Linux
для ограничения, учёта и изоляции потребления ресурсов (процессорное время,
память, дисковый и сетевой ввод-вывод) группой процессов.

<div class="grid grid-cols-2 gap-4 mt-3">
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10">
<b>Что умеет сверх <code>ulimit</code></b><br/>
ограничивает <b>совокупное</b> потребление группы процессов, а не каждого
по отдельности; поддерживает несколько моделей распределения
</div>
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10">
<b>Основа контейнеризации</b><br/>
изоляция и учёт ресурсов для <code>systemd</code>-служб, LXC и Docker
опираются именно на <code>cgroup2</code>
</div>
</div>

<div class="mt-3 p-2 border-l-4 border-teal-500 bg-teal-500/10 text-xs">
<code>cgroup</code> выполняет функции, сходные с <code>ulimit</code> +
<code>limits.conf</code> и <Man p="nice(1)" />, но делает это
<b>гибче</b>: на уровне произвольной группы процессов, с иерархией и
несколькими моделями распределения (раздел 3.5).
</div>

<Refs ids="cgroups-wiki kernel-cgroup-v2 kerrisk-cgroup-intro" />

# Два базовых компонента: ядро иерархии и контроллеры

<div class="grid grid-cols-2 gap-4 mt-3">
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10">
<b>Ядро механизма</b><br/>
строит <b>иерархию групп управления</b> — размещает процессы по группам,
образующим единое дерево
</div>
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10">
<b>Контроллеры ресурсов</b><br/>
объекты ядра, управляющие потреблением <b>конкретного</b> ресурса
(<code>cpu</code>, <code>memory</code>, <code>pids</code>, <code>io</code>…)
по иерархии
</div>
</div>

<div class="mt-4">

**Группа управления** (`cgroup`) — множество процессов, объединённых для
управления их совокупным потреблением ресурсов. Правила размещения:

<div class="t-table text-xs mt-2">

| Правило | Следствие |
|---|---|
| каждый процесс принадлежит **ровно одной** группе | иерархия групп разбивает процессы на непересекающиеся подмножества |
| все потоки процесса — в той же группе | группа — единый «домен ресурсов» для потоков |
| при `fork(2)` потомок попадает в группу родителя | по умолчанию поддерево процессов наследует группу |
| процесс можно перенести в другую группу | перенос родителя **не** затрагивает уже созданных потомков |

</div>
</div>

<div class="mt-3 p-2 border-l-4 border-teal-500 bg-teal-500/10 text-xs">
Контроллер иногда называют <i>подсистемой</i> (<i>subsystem</i>), однако
этот термин многозначен, и его употребления рекомендуется избегать.
</div>

<Refs ids="kernel-cgroup-v2 kerrisk-cgroup-intro" />

<!--
Два компонента механизма: ядро (строит дерево групп и распределяет по нему
процессы) и контроллеры (по одному на вид ресурса). Определение cgroup как
множества процессов с совокупным учётом. Четыре правила размещения в
таблице — они понадобятся в демонстрациях 3.3: ровно одна группа на
процесс, потоки вместе, наследование при fork, независимость уже созданных
потомков при переносе родителя. Бирюзовое замечание — терминологическая
гигиена из документации ядра: «подсистема» = контроллер, но слово
перегружено, используем «контроллер».
-->

# Иерархия групп управления отличается от дерева процессов

Процессы Unix образуют дерево с корнем `init`. Группы управления строят
**отдельное** дерево: они разбивают процессы на непересекающиеся
поддеревья, но могут отступать от родственных связей процессов.

<BlockFlow class="mt-4 mb-3" size="0.82em" :blocks="[
  { head: 'Дерево процессов', sub: 'init → потомки\n(родственные связи)' },
  { head: 'cgroup.procs', mono: true, sub: 'запись PID\nпереносит процесс' },
  { head: 'Иерархия cgroup', sub: 'непересекающиеся\nподмножества процессов' },
]" :arrows="['разбивается на', 'задаёт']" />

<div class="grid grid-cols-2 gap-3 mt-2">
<div class="p-3 border-l-4 border-amber-500 bg-amber-500/10 text-xs">
<b>Независимость от дерева процессов</b><br/>
один дочерний процесс можно перенести в произвольную группу, оставив
родителя в прежней — связи процессов и групп расходятся
</div>
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
<b>Единый интерфейс — файловые операции</b><br/>
конфигурирование сводится к чтению и записи интерфейсных файлов: из
оболочки, программно, через <code>systemd</code> или LXC/Docker
</div>
</div>

<div class="mt-3 p-2 border-l-4 border-teal-500 bg-teal-500/10 text-xs">
Интерфейс предоставляется <b>псевдофайловой системой</b> <code>cgroup2</code>,
смонтированной в <code>/sys/fs/cgroup</code>. Структура каталога группы
задаёт её параметры, множество процессов и подгруппы.
</div>

<Refs ids="kernel-cgroup-v2 kerrisk-cgroup-intro man-cgroups" />

<!--

администратор может их развести: перенести один потомок, оставив родителя.

# Конфигурирование — это файловые операции над /sys/fs/cgroup

<div class="grid grid-cols-2 gap-5 mt-3">
<div>

**Подгруппа создаётся как каталог:**

- <Man p="mkdir(2)" /> в точке монтирования создаёт группу; ядро
  автоматически наполняет её **интерфейсными файлами**;
- <Man p="rmdir(2)" /> удаляет группу — но только пустую (без процессов
  и подгрупп).

Интерфейсные файлы служат для:

1. задания множества процессов группы;
2. настройки контроллеров ресурсов;
3. вывода статистики потребления.

</div>
<div>

**Группы файлов в каталоге группы** (<Man p="cgroups(7)" />):

<div class="t-table text-xs mt-1">

| Файл | Назначение |
|---|---|
| `cgroup.procs` | список PID процессов группы |
| `cgroup.controllers` | доступные контроллеры |
| `cgroup.subtree_control` | включённые контроллеры |
| `cgroup.stat` | структура группы |
| `cgroup.events` | населённость поддерева |
| `cpu.*`, `memory.*`, `pids.*` | конфигурация контроллеров |

</div>

</div>
</div>

<div class="mt-3 p-2 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
Префикс имени файла указывает принадлежность: <code>cgroup.*</code> — общие
файлы группы, <code>&lt;controller&gt;.*</code> — файлы конкретного
контроллера. Это соглашение сохраняется во всех группах иерархии.
</div>

# Процесс принадлежит ровно одной группе единой иерархии

<div class="grid grid-cols-2 gap-5 mt-3">
<div>

**Следствия единой иерархии:**

- добавление процесса в группу **автоматически** удаляет его из прежней;

# Управление ресурсами возможно на уровне потоков

По умолчанию все потоки процесса находятся в одной группе — она служит
**доменом ресурсов**. **Режим потоков** (*thread mode*) позволяет
распределять потоки одного процесса по поддереву групп.

<div class="t-table text-xs mt-3">

| Значение `cgroup.type` | Смысл |
|---|---|
| `domain` | обычная группа: содержит процессы и подгруппы |
| `domain threaded` | корень потокового поддерева (*threaded subtree*) |
| `threaded` | группа, управляющая потреблением ресурсов **потоками** |
| `domain invalid` | группа в некорректном (переходном) состоянии |

</div>

<div class="grid grid-cols-2 gap-3 mt-3">
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
<b>Потоковые контроллеры</b><br/>
поддерживают режим потоков: <code>cpu</code>, <code>cpuset</code>,
<code>perf_event</code>, <code>pids</code>
</div>
<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
<b>Доменные контроллеры</b><br/>
работают только на уровне процессов (например, <code>memory</code>):
память не делится между потоками процесса
</div>
</div>

<div class="mt-3 p-2 border-l-4 border-amber-500 bg-amber-500/10 text-xs">
Запись `PID` любого потока в `cgroup.procs` переносит <b>все</b> потоки
процесса; распределение отдельных потоков выполняется через
`cgroup.threads` в потоковом поддереве.
</div>

<Refs ids="kernel-cgroup-v2 kerrisk-cgroup-deep" />

<!--

<div><span class="co-ball">3</span> запись <code>+cnt</code>/<code>-cnt</code> включает/выключает; одной операцией — несколько контроллеров</div>
<div><span class="co-ball">4</span> после записи включены <code>cpu</code> и <code>memory</code> (строка <code>-io</code> ничего не выключила: <code>io</code> и не был включён)</div>
</div>
</div>
</div>

<div class="mt-2 p-2 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
Множество включённых (<code>subtree_control</code>) всегда является
<b>подмножеством</b> доступных (<code>controllers</code>). По умолчанию
не включён ни один контроллер.
</div>

# Иерархию ограничивают правила «сверху вниз» и «без внутренних процессов»

<div class="grid grid-cols-[1fr_1.05fr] gap-4 mt-2 items-start">
<div>

<div class="p-3 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
<b>Ограничение сверху вниз</b> (<i>top-down</i>)<br/>
контроллер можно включить в группе, только если он включён у родителя;
ресурс распределяется от корня к листьям
</div>

<div class="mt-2 p-3 border-l-4 border-sky-500 bg-sky-500/10 text-xs">
<b>Без внутренних процессов</b> (<i>no internal process</i>)<br/>
группа с включёнными контроллерами не может содержать собственные
процессы — процессы допустимы только в листьях
</div>

<TerminalCapture content="A(cpu,memory) ── B(memory) ── C()

# Контроллеры используют четыре модели распределения

Контроллер выбирает модель в зависимости от природы ресурса. Модели
различаются тем, можно ли «перегрузить» ресурс (*over-commit*) — назначить
потомкам в сумме больше, чем есть у родителя.

<div class="t-table text-xs mt-3">

| Модель | Что задаёт | Диапазон / умолчание | Over-commit | Пример |
|---|---|---|---|---|
| **Веса** (weights) | долю ресурса пропорционально весу среди активных потомков | `[1, 10000]` / `100` | — (динамическая доля) | `cpu.weight` |
| **Лимиты** (limits) | верхний предел потребления | `[0, max]` / `max` | допустим | `cpu.max` |
| **Защита** (protections) | гарантированный минимум при конкуренции | `[0, max]` / `0` | допустима | `memory.low` |
| **Бронирование** (allocations) | монопольно выделенное количество | `[0, max]` / `0` | **запрещён** | `cpu.rt.max` |

</div>

<div class="grid grid-cols-2 gap-3 mt-3 text-xs">
<div class="p-2 border-l-4 border-sky-500 bg-sky-500/10">
<b>Веса</b> обеспечивают полную загрузку ресурса: в распределении участвуют
только потомки, способные использовать ресурс сейчас, поэтому простаивающая
доля переходит активным.
</div>
<div class="p-2 border-l-4 border-amber-500 bg-amber-500/10">
<b>Бронирование</b> нельзя перегрузить: сумма резервов потомков не может
превысить ресурс родителя, поэтому часть конфигураций ядро отклоняет.
</div>
</div>

<Refs ids="kernel-cgroup-v2 kerrisk-cgroup-deep" />

<!--
Четыре модели распределения — ядро темы 3.5. Ось различения: допускает ли
модель over-commit (сумма у потомков > ресурс родителя). Веса
(пропорциональное распределение активных потомков, диапазон 1–10000,
умолчание 100 ради процентов; work-conserving — простаивающее отдаётся
активным; для ресурсов без состояния, напр. CPU). Лимиты (жёсткий потолок,
max по умолчанию = без ограничения, over-commit допустим). Защита
(гарантированный минимум при конкуренции, best-effort или hard, напр.
memory.low). Бронирование (монопольное выделение, over-commit ЗАПРЕЩЁН,
поэтому ядро отклоняет недопустимые конфигурации, напр. cpu.rt.max).
Два блока внизу выделяют крайние случаи: work-conserving у весов и
неперегружаемость брони. В демо 3.6 используем модель лимитов (cpu.max).

# Итоги: два механизма разграничения ресурсов

<div class="t-table text-xs mt-3">

| Критерий | Лимиты ресурсов (`ulimit`) | Группы управления (`cgroup2`) |
|---|---|---|
| Единица | процесс (и его поддерево); пользователь через PAM | группа процессов в единой иерархии |
| Предмет | предел на каждый процесс по отдельности | совокупное потребление группы |
| Модель | мягкий / жёсткий лимит | веса, лимиты, защита, бронирование |
| Настройка | `ulimit`, `limits.conf`, `setrlimit()` | файловые операции над `/sys/fs/cgroup` |
| Граница применимости | не сдерживает множество процессов совместно | требует привилегий; сложнее в настройке |

</div>

<div class="mt-3 p-3 border-l-4 border-teal-500 bg-teal-500/10">
Исчерпание ресурсов — класс угроз <b>доступности</b>, неподвластный
механизмам разграничения доступа. Linux противопоставляет ему два
взаимодополняющих средства: <b>лимиты ресурсов</b> дают лёгкое ограничение
на уровне процесса и пользователя, а <b>группы управления</b>
(<code>cgroup2</code>) — гибкое иерархическое распределение совокупного
потребления групп процессов. На <code>cgroup2</code> опираются изоляция и
учёт ресурсов в <code>systemd</code> и системах контейнеризации — предмет
следующей темы.
</div>

<Refs ids="kerrisk-tlpi kernel-cgroup-v2 man-cgroups" />

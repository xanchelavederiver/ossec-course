[#section-chroot]
== Механизм chroot в Unix/Linux

Механизм `chroot` (_change root_) — один из самых ранних способов изоляции процессов в Unix-подобных операционных системах. Он позволяет изменить корневой каталог (`/`) для процесса и всех его потомков, создавая _иллюзию_ работы процессов в отдельной файловой системы{nbsp}<<Wiki-chroot>><<Wiki-archlinux-chroot>>.

В настоящем разделе кратко рассмотрена история, назначение и внутренние механизмы работы `chroot`, практические примеры использования, а также приведено сравнение с современными контейнерными технологиями.

=== Краткий исторический обзор

`chroot` был представлен в *Unix Version 7* в 1979 году, предположительно Биллом Джой (Bill Joy), одним из разработчиков BSD.

Изначально `chroot` создавался:

* как инструмент тестирования,
* для отладки программ в альтернативной файловой иерархии.

[NOTE]
====
Изначально `chroot` *не задумывался* как механизм безопасности.
====

Со временем `chroot` был перенят BSD, System V и Linux и стал использоваться для запуска сетевых сервисов.

`chroot` оказал влияние на появление более сложных механизмов изоляции:

* FreeBSD Jails;
* Solaris Zones;
* Linux Containers (LXC);
* Docker.

=== Назначение chroot

`chroot` изменяет корневой каталог процесса, тем самым ограничивая доступ процесса к файловой системе.

Основная идея: процесс "видит" только ту часть файловой системы, которая находится внутри нового корня.

.Назначение chroot
[cols="1,2"]
|===
^|Проблема ^|Как chroot помогает

|Случайное повреждение системы
|Процесс не имеет доступа к реальному `/`

|Тестирование ПО
|Использование альтернативных `/lib`, `/etc`

|Ограничение ущерба
|Компрометация сервиса ограничена файловой системой

|Восстановление системы
|Работа с установленной ОС из Live-среды
|===

[IMPORTANT]
====
`chroot` *не является* полноценной границей безопасности (_chroot is not a security boundary_) так как:

* не создает новые пространства имён (_namespace_, см. <<section-namespaces>>) процессов;
* не ограничивает системные вызовы;
* не фильтрует сетевой трафик;
* не способен пользователю `root` выйти из `chroot jail` при неправильной настройке.
====

Механизм `chroot` **не изолирует**:

* сеть;
* процессы;
* пользователей;
* ядро;
* IPC;
* системные вызовы.

[#section-chroot_inner-workins]
=== Механизм работы chroot

==== Системный вызов chroot()

`chroot jail` создаётся посредством команды link:{man-chroot_1}[chroot(1)] или системного вызова link:{man-chroot_2}[chroot(2)]:
[source,c]
----
#include <unistd.h>

int chroot(const char *path);
----

Системный вызов link:{man-chroot_2}[chroot(2)]:

* доступен только привилегированным процессам (`root`);
* изменяет указатель корневого каталога процесса;
* влияет только на текущий процесс и его потомков.

==== Разрешение путей

Внутри `chroot jail` выполняется трансляция (разрешение) путей:

. В абсолютных путях переписываются префиксы
* до `chroot`
+
----
/etc/passwd → /etc/passwd
----
+
* после `chroot("/newroot")`
+
----
/etc/passwd → /newroot/etc/passwd
----
. Относительные пути продолжают разрешаться относительно текущего каталога.

==== Пример создания chroot jail

В качестве примера использования `chroot` создадим небольшую песочницу с корнем в директории `/tmp/chroot-test`.

.1. Пробуем запустить `/bin/bash` с корнем на `/tmp/chroot-test`
[source,console]
----
$ mkdir /tmp/chroot-test
$ sudo chroot /tmp/chroot-test /bin/bash
chroot: failed to run command ‘/bin/bash’: No such file or directory
----

Ошибка: не найден исполняемый файл командной оболочки.

Так как `chroot` создаёт новую, изолированную файловую систему, которая не имеет доступа к основной, все файлы оригинальной системы оказываются недоступны - в том числе и `/bin/bash`.

.2. Копируем `/bin/bash` в корень `/tmp/chroot-test` до запуска `chroot`

[source,console]
----
$ mkdir /tmp/chroot-test/bin
$ cp /bin/bash /tmp/chroot-test/bin
$ sudo chroot /tmp/chroot-test /bin/bash
chroot: failed to run command ‘/bin/bash’: No such file or directory
----

Опять ошибка! Однако, несмотря на идентичное сообщение, совсем не такая, как в прошлый раз.

В первой попытке не был найден сам исполняемый файл `/bin/bash`, теперь же не найдены динамически подключаемые библиотеки (`*.so`), с которыми скомпилирован интерпретатор.

.3. Копируем все зависимости в корень `/tmp/chroot-test` до запуска `chroot`

Посмотреть, какие именно динамические библиотеки требуется скопировать, можно с помощью `ldd`:

[source,console]
----
$ ldd /bin/bash
        linux-vdso.so.1 (0x000079298c924000)
        libtinfo.so.6 => /lib/x86_64-linux-gnu/libtinfo.so.6 (0x000079298c76e000)
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x000079298c400000)
        /lib64/ld-linux-x86-64.so.2 (0x000079298c926000)
----

Копируем зависимости и попробуем:
[source,console]
----
$ mkdir /tmp/chroot-test/lib /tmp/chroot-test/lib64
$ cp /lib/x86_64-linux-gnu/libtinfo.so.6 /tmp/chroot-test/lib/
$ cp /lib/x86_64-linux-gnu/libc.so.6 /tmp/chroot-test/lib
$ cp /lib64/ld-linux-x86-64.so.2 /tmp/chroot-test/lib64/
$ sudo chroot /tmp/chroot-test /bin/bash
bash-5.2#
----

[NOTE]
====
Удобно настроить приглашение командной оболочки (_prompt_), дабы отличать среду `chroot jail` от основной, для этого в `chroot jail` выполнить:
[source,console]
----
export PS1="(chroot) $PS1"
----

Продолжая текущий пример:
[source,console]
----
$ sudo chroot /tmp/chroot-test /bin/bash
bash-5.2# export PS1="(chroot) $PS1"
(chroot) bash-5.2#
----
====

[#section-chroot_inner-workins-chroot_jail_correct]
==== Пример корректного создания chroot jail

Для полноценного функционирования ОС в `chroot jail` необходимо выполнить несколько подготовительных операций{nbsp}<<Wiki-archlinux-chroot>>.

[WARNING]
====
Конкретные шаги могут отличаться для различных дистрибутивов. В настоящем разделе показан пример подготовки окружения в Ubuntu 24.04.
====

.1. Подготавливаем окружение

[source,console]
----
$ mkdir /tmp/chroot-test2
$ mkdir /tmp/chroot-test2/{proc,sys,dev,run}
----
[source,console]
----
$ sudo mount -t proc proc /tmp/chroot-test2/proc/
$ sudo mount -t sysfs /sys /tmp/chroot-test2/sys/
$ sudo mount --rbind /dev /tmp/chroot-test2/dev/
$ sudo mount --rbind /run /tmp/chroot-test2/run/
----

.2. Копируем необходимые исполняемые файлы и зависимости и работаем

Далее требуется либо скопировать исполняемые файлы и их зависимости, как показано в предыдущем примере.

Альтернативный вариант: смонтировать директории `/bin`, `/lib`, `/lib32`, `/lib64` и т.п. в одноимённые поддиректории корня:

[source,console]
----
$ mkdir /tmp/chroot-test2/{bin,lib,lib64}
$ sudo mount --rbind /bin /tmp/chroot-test2/bin
$ sudo mount --rbind /lib /tmp/chroot-test2/lib
$ sudo mount --rbind /lib64 /tmp/chroot-test2/lib64
----

Далее работаем в окружении:

[source,console]
----
$ sudo chroot /tmp/chroot-test2 /bin/bash
bash-5.2# export PS1="(chroot) $PS1"
(chroot) bash-5.2#
----

.3. Зачищаем окружение

[source,console]
----
$ sudo umount /tmp/chroot-test2/lib64
$ sudo umount /tmp/chroot-test2/lib
$ sudo umount /tmp/chroot-test2/bin
----

[source,console]
----
$ sudo umount /tmp/chroot-test2/proc
$ sudo umount /tmp/chroot-test2/sys
$ sudo umount -l /tmp/chroot-test2/run
$ sudo umount -l /tmp/chroot-test2/dev
----

[IMPORTANT]
====
Чаще всего отмонтировать `dev/` и `run/` без флага `-l` (_lazy_) не получится, поэтому рекомендуется сразу по завершении работы с `chroot jail` выполнить перезагрузку системы.
====

=== Практические примеры использования механизма chroot

==== Пример 1: изоляция приложения

Одно из основных назначений `chroot` - запуск приложения в изолированном окружении.

[NOTE]
====
Последовательность действий аналогична примерам, показанным в примерах раздела <<section-chroot_inner-workins>>.
====

Для этого сначала требуется создать минимальное окружение:

[source,console]
----
$ mkdir -p /chroot/{bin,lib,lib64,...}
$ cp /bin/bash /chroot/bin/
...
----

Далее выполнить копирование исполняемых файлов и их зависимостей (библиотек `.so`):

[source,console]
----
$ ldd my-program
$ cp /lib/x86_64-linux-gnu/libc.so.6 /chroot/lib/
$ cp /lib64/ld-linux-x86-64.so.2 /chroot/lib64/
...
----

Выполнить вход в окружение:

[source,console]
----
$ chroot /chroot my-program
----

В результате процесс `my-program` не будет иметь доступ к большей части файловой системы ОС.

Примеры использования такого подхода в реальных системах:

* изоляция сетевых служб (FTP, DNS, SMTP и др.);
* recovery-среды, debug-билды, системные утилиты в ОС Linux (в частности, в Android OS).

==== Пример 2: восстановление системы

`chroot` часто используется для восстановления системы, а также для создания загрузочных образов (см.{nbsp}<<Build-custom-livecd>>).

Типичный сценарий восстановления повреждённой системы:

. Грузимся с помощью LiveCD.
. Монтируем файловую систему повреждённой ОС, а также ряд служебных псевдофайловых систем:
+
[source,bash]
----
$ sudo mount /dev/sda2 /mnt
$ sudo mount --bind /dev /mnt/dev
$ sudo mount --bind /proc /mnt/proc
$ sudo mount --bind /sys /mnt/sys
----
. Запускаем `chroot`:
+
[source,bash]
----
$ sudo chroot /mnt /bin/bash
...
----
. Выполняем необходимые команды: например, установка пакетов, редактирование конфигурационных файлов, пересборка initramfs и т.п.

[NOTE]
====
Подобный подход применялся нами для сброса пароля `grub`.
====

==== Пример 3: тестирование библиотек

Аналогично тестированию приложения:

. создается альтернативное `/lib`;
. приложение запускается в `chroot`;
. выполняется тестирование с альтернативным набором библиотек.

=== Заключение

* `chroot` - исторически важный механизм.
* Механизм `chroot` прост, но его возможности ограничены.
* Подходит для:
** восстановления системы;
** тестирования;
** legacy-сценариев.
* Не должен рассматриваться как полноценная защита.
* Современные контейнеры являются логическим развитием идей `chroot`.

=== Краткий исторический обзор

Пространства имён Linux (*Linux namespaces*) - механизм ядра, обеспечивающий изоляцию глобальных системных ресурсов между группами процессов{nbsp}<<Namespaces-lwn-overview>><<Namespaces-toptal-intro>><<Namespaces-habr-intro>>.

* *2002–2003*: первым было реализовано *пространство файловой системы* (*mount namespace*, Linux{nbsp}2.4.19), позволившее процессам иметь разные представления таблицы монтирования.
* *2006–2008*: были добавлены UTS, IPC, PID и Network namespaces.
* *2013 (Linux 3.8)*: завершена реализация поддержки пространств имён пользователей (*user namespaces*), что позволило непривилегированным пользователям создавать пространства имён и создавать пользователей `root` внутри контейнера.

Пространства имён - фундамент контейнерных технологий (LXC, Docker, Podman), обеспечивающий лёгкую виртуализацию без запуска отдельного ядра.

=== Назначение механизма пространств имён

Основная идея — *изоляция глобальных ресурсов ядра*. Вместо одного общего пространства процессов, сети или единой файловой системы каждая группа процессов получает собственное представление этих ресурсов.

Namespaces применяются для:

* разрешения конфликты ресурсов (PID, порты, имена хостов);
* повышения безопасности за счёт изоляции процессов;
* запуска приложений, ожидающих «полноценную» систему - зачастую настроенную иначе, чем основная ("хостовая");
* лёгковесная виртуализация (вместо тяжёлых виртуальных машин, загружающих полноценную ОС).

=== Основные типы пространств имён

[cols="1,3",options="header"]
|===
| Пространство имён | Что изолируется
| PID | Идентификаторы процессов (PID)
| Network | Сетевой стек (интерфейсы, порты и проч.)
| User | Идентификаторы пользователей (UID) и групп (GID)
| Mount | Точки монтирования (части файловой системы)
| IPC | SystemV IPC, очереди сообщений POSIX
| UTS | Имя хоста (`hostname`) и доменное имя NIS (`domainname`)
|===

[#section-namespaces_mount]
=== Пространство имён Mount (CLONE_NEWNS)

==== О пространстве имен монтирования

Пространства имен монтирования, *Mount namespace* - мощный и гибкий инструмент создания собственных представлений дерева файловой системы ОС, видимых пользователям и процессам{nbsp}<<Namespaces-lwn-mount-ns>><<Namespaces-lwn-mount-ns-2>>.

Пространства имен монтирования появились в версии 2.4.19 в 2002 году и стали первым типом пространств имен, реализованным в Linux.

Mount namespace изолируют список точек монтирования, видимых процессам в пространстве имен. Для каждого пространства имен монтирования определён *свой собственный* список точек монтирования, видимый только процессам в этом пространстве. В результате процессы в разных пространствах имён видят и манипулируют разными *представлениями одной и той же иерархии* каталогов.

При загрузке системы создаётся одно пространство имен монтирования, называемое _исходное_ пространство имен (_initial namespace_), также основное или главное. Новые пространства имен монтирования создаются с помощью вызова:

* link:{man-clone_2}[clone(2)] с флагом `CLONE_NEWNS` - создаётся новое пространство имён и новый процесс, помещаемый в это пространство;
* link:{man-unshare_2}[unshare(2)] - текущий процесс перемещается в новое пространство имён.

После вызова link:{man-clone_2}[clone(2)] или link:{man-unshare_2}[unshare(2)] точки монтирования *могут* быть добавлены и удалены в каждом пространстве имён независимо друг от друга (с помощью link:{man-mount_2}[mount(2)] и link:{man-umount_2}[umount(2)]). Изменения в списке точек монтирования видны только процессам в пространстве имён монтирования, в котором находится процесс и не видны в других пространствах имён монтирования.

[IMPORTANT]
====
Изменения в списке точек монтирования одного пространства имён могут быть видны в других пространствах в случае использования т.н. общих поддеревьев, см. раздел <<section-namespaces_mount-shared_subtrees>>.
====

Пространства имен монтирования служат для различных целей, в частности:

. создание пользовательских представлений файловой системы - изоляция файлов пользователей;
. изоляции рабочих директорий процессов в стиле т.н. chroot-jail (см. <<section-chroot_inner-workins-chroot_jail_correct>>);
. монтирование файловой системы `/proc` для нового пространства имен PID (см. <<section-namespaces_pid>>);
. создание собственной корневой файловой системы (_root filesystem_) для контейнеров.

===== Отличие от chroot

link:{man-chroot_2}[chroot(2)] меняет только корневой каталог процесса, в отличие от пространства имён Mount, которое также изолирует таблицу монтирования, события файловой системы и проч.

Mount namespace - обобщение и расширение механизма `chroot`.

==== Группы точек монтирования (peer groups)

*Точкой монтирования* (*mount point*) называют файл или директорию файловой системы, ассоциируемую с некоторым устройством (HDD, SSD, флешка, CD-ROM), другим файлом или директорией. В случае связывания нового файла/директории с существующим файлом/директорией файловой системы тип монтирования называют _бинд-монтирование_ (_bind mount_).

В некотором смысле бинд-монтирование похоже на создание жёсткой ссылки (hard link), но имеет важные отличия{nbsp}<<Namespaces-lwn-mount-ns-2>>:

* нельзя создать жёсткую ссылку на директорию, однако можно выполнить бинд-монтирование директории;
* жёсткие ссылки возможны только в пределах одной файловой системы, тогда как бинд-монтирование может пересекать границы файловых систем (и даже выходить за пределы `chroot()`-окружения);
* жёсткие ссылки требуют изменения файловой системы, бинд-монтирование же является записью в списке монтирования пространства имён монтирования - изменения отражаются в оперативной памяти работающей системы.

Бинд-монтирование можно создать программно с помощью системного вызова link:{man-mount_2}[mount(2)] с флагом `MS_BIND` или из командной строки с помощью `mount --bind`.

*Группа точек монтирования* (*peer group*) - набор точек монтирования, объединяемых для передачи друг другу событий монтирования и размонтирования.

====
Проиллюстрируем концепцию на примере. Предположим, в файловой системе определена точка монтирования `/` и три точки монтирования `A`, `B`, `C`, объединённые в группу `M`:

----
/       <- /dev/sda1
├── A   <- /dev/sdb1   ─┐
├── B   <- /dev/sdb2   ─┼ M
└── C   <- /dev/sdb3   ─┘
----

Предположим, *непосредственно под точкой монтирования* `A` выполняется монтирование нового устройства - создаётся точка `X`.

[NOTE]
=====
"Непосредственно под" означает, что между `A` и `X` отсутствуют другие точки монтирования в поддереве файловой системы с корнем в `X`.
=====

Так как точка `A` состоит в группе точек монтирования `M`, событие "монтирование `X`{zwsp}" транслируется (is propagated) точкам `B` и `C`, что приводит к следующий картине:

----
/           <- /dev/sda1
├── A       <- /dev/sdb1   ─┐
    └── X   <- /dev/sdc    ─┤
├── B       <- /dev/sdb2   ─┼ M
    └── X   <- /dev/sdc    ─┤
└── C       <- /dev/sdb3   ─┤
    └── X   <- /dev/sdc    ─┘
----
====

Точка монтирования `X` типа `MS_SHARED` (см.{nbsp}<<section-namespaces_mount-shared_subtrees, следующий раздел>>) добавляется в группу точек в следующих случаях:

. точка монтирования `X` реплицируется при создании нового пространства имён монтирования;
. точка `X` бинд-монтируется.

В обоих случаях новая точка становится членом той же группы точек монтирования, что и существующая точка `X`.

Точка монтирования перестает быть членом группы, когда она размонтируется, либо явно с помощью системного вызова link:{man-umount_2}[umount(2)], либо неявно, когда пространство имен монтирования уничтожается из-за завершения последнего процесса-члена или его перехода в другое пространство имен.

[#section-namespaces_mount-shared_subtrees]
==== Общие поддеревья (shared subtrees)

Как показала практика применения только что реализованного механизма пространств имён монтирования, изоляция пространств может быть чрезмерной{nbsp}<<Namespaces-lwn-mount-ns>>.

Типичный пример ситуации, доставляющей значительные неудобства при работе с полностью изолированными окружениями: монтирование диска в приводе CD-ROM. В первоначальной реализации единственным способом сделать этот диск видимым во всех пространствах имён монтирования было выполнение отдельного монтирования диска в каждом пространстве имён. Во многих случаях предпочтительнее было бы выполнить одну операцию монтирования, которая сделает диск видимым во всех (или, возможно, в некотором подмножестве) пространств имён системы.

Для решения описанной проблемы в Linux 2.6.15 (в начале 2006 года) был добавлен механизм *общих поддеревьев* (*shared subtrees*). Механизм общих поддеревьев обеспечивает автоматическое и контролируемое распространение событий монтирования и размонтирования между членами группы точек монтирования (peer group).

Продолжая пример с монтированием оптического диска, наличие общих поддеревьев позволяет выполнить однократное монтирование диска, что повлечёт за собой монтирование в остальных членах соответствующей группы.

Характер распространения событий монтирования определяется *типом распространения* (*propagation type*) точки. Определены четыре типа:

* `MS_SHARED` - точка монтирования делится событиями монтирования и размонтирования с другими точками своей peer group, в результате монтирование или размонтирование также произойдёт под каждой из точек монтирования группы. Аналогично в обратном направлении: точка получает события от других точек группы.
* `MS_PRIVATE` - в противоположность типу `MS_SHARED`, точка монтирования не делится событиями с другими точками и не получает события от них.
* `MS_SLAVE` - нечто среднее между типами `MS_SHARED` и `MS_PRIVATE`, точка монтирования получает события от своей _главной_ группы точек, но не передаёт свои события членам группы.
* `MS_UNBINDABLE` - аналогично `MS_PRIVATE`, точка не передаёт и не получает события от других точек группы. Кроме этого, точку монтирования невозможно привязать к другой точке с помощью бинд-монтирования.

Важно отметить следующие особенности:

. Тип `MS_UNBINDABLE` решает проблему, именуемую "mount point explosion" (см.{nbsp}<<Namespaces-lwn-mount-ns-2>>); в контексте пространств имён монтирования этот тип фактически является аналогом `MS_PRIVATE`.
// TODO: проверить - возможно, у MS_UNBINDABLE имеются side-эффекты!
. Термин "событие монтирования" носит концептуальный характер: операция монтирования не порождает никаких событий (в понимании очередей сообщений и т.п.), однако провоцирует проверки наличия соседей по peer group родительской точки монтирования и монтирование в этих точках группы.
. Тип распространения - характеристика точки монтирования, а не пространства имён монтирования. В одном пространстве могут одновременно находится множество точек монтирования разных типов.
. При выполнении операции монтирования или размонтирования решение о распространении события определяется типом *непосредственно родительской* точки монтирования.
+
Например, при монтировании точки `Y` *непосредственно* под точкой `X` типа `MS_SHARED` это событие будет передано всем членам группы точек, в которой состоит `X`. В случае монтирования точек под `Y` распространение событий будет определяться типом точки `Y`, а не `X`.
. Точка монтирования может быть одновременно `MS_SLAVE` и `MS_SHARED` (т.н. slave-and-shared mount). В этом случае точка будет получать события от своей главной группы и передавать эти события членам её разделяемой группы.

==== Файл /proc/<PID>/mountinfo

Информация о точках монтирования пространства имён монтирования отображается в файле `/proc/<PID>/mountinfo`, где <PID> - идентификатор любого процесса, находящегося в пространстве имён. В каждую запись этого файла включён (возможно, пустой) набор опциональных полей (optional fields), которые отображают информацию о типе распространения и группе точек монтирования для каждой точки монтирования пространства имён{nbsp}<<Namespaces-lwn-mount-ns>>.

. Для точки типа `MS_PRIVATE` опциональные поля пусты.
. Точки типа `MS_UNBINDABLE` отмечены полем `unbindable`.
. Для точки типа `MS_SHARED` опциональные поля содержат метку вида `shared:<N>`, где тег `shared` указывает на тип точки, а целое число `N` задаёт уникальный идентификатор группы точек монтирования. Идентификаторы группы нумеруются, начиная с 1, и могут повторно использоваться, когда группа перестаёт существовать (из-за того, что все её члены покинули группу). Для всех точек монтирования, являющихся членами одной группы, в файле `mountinfo` отображается тег `shared:<N>` с одним и тем же идентификатором `N`.
. Точка типа `MS_SLAVE` отображается меткой вида `master:<N>`, где `N` - номер главной группы peer group.

==== Пример: типы распространения и файл mountinfo

===== MS_PRIVATE и MS_SHARED

Создадим приватную и разделяемую точки монтирования:

[source,console,options="nowrap"]
----
$ mkdir -p /tmp/mounts/{private,shared}  <1>
$ sudo mount -t tmpfs tmpfs /tmp/mounts/private
$ sudo mount -t tmpfs tmpfs /tmp/mounts/shared

$ cat /proc/self/mountinfo | grep mounts  <2>
63 30 0:44 / /tmp/mounts/private rw,relatime shared:64 - tmpfs tmpfs rw,inode64
414 30 0:56 / /tmp/mounts/shared rw,relatime shared:261 - tmpfs tmpfs rw,inode64

$ sudo mount --make-private /tmp/mounts/private  <3>
$ sudo mount --make-shared /tmp/mounts/shared    <4>
$ cat /proc/self/mountinfo | grep mounts
63 30 0:44 / /tmp/mounts/private rw,relatime - tmpfs tmpfs rw,inode64  <5>
414 30 0:56 / /tmp/mounts/shared rw,relatime shared:261 - tmpfs tmpfs rw,inode64  <6>
----
<1> Создаём две точки монтирования tmpfs (RAM-based временная FS)
<2> В выводе файла `/proc/self/mountinfo` видим тип созданных точек - `MS_SHARED`, т.к. опциональные поля содержат теги `shared:64` и `shared:261`, соответственно +
*N.B.* Процесс оболочки `bash` находится в исходном пространстве имён монтирования, там же, где созданы обе точки монтирования, поэтому информацию можно получить с помощью `/proc`, используя PID `bash` (через подстановку `self`)
<3> Изменяем тип точки `/tmp/mounts/private` на `MS_PRIVATE`
<4> Изменяем тип точки `/tmp/mounts/shared` на `MS_SHARED`
<5> Новый тип точки `/tmp/mounts/private` - `MS_PRIVATE` (опциональные поля отсутствуют)
<6> Тип точки `/tmp/mounts/shared` не изменился - `MS_SHARED`

[NOTE]
====
Обратите внимание на ID точек монтирования: 63 у `private` и 414 у `shared`. Также точка `shared` состоит в группе точек монтирования с ID=261.
====

В другой консоли создадим новое пространство имён и проверим список точек монтирования:

[source,console,options="nowrap"]
----

# export PS1="(mount ns) $PS1"

(mount ns) # cat /proc/self/mountinfo | grep mounts
652 434 0:44 / /tmp/mounts/private rw,relatime - tmpfs tmpfs rw,inode64  <2>
653 434 0:56 / /tmp/mounts/shared rw,relatime shared:261 - tmpfs tmpfs rw,inode64  <3>
----
<1> Создаём пространство имён монтирования +
*N.B.* По умолчанию утилита `unshare` изменяет тип клонируемых точек монтирования на `MS_PRIVATE`; чтобы оставить тип неизменным, необходимо использовать `--propagation unchanged`
<2> В новом Mount namespace тип точки `/tmp/mounts/private` остался неизменным, а ID новый - 652 (т.е. это новая точка монтирования, а не ссылка на точку с ID=63)
<3> В новом Mount namespace тип точки `/tmp/mounts/shared` остался неизменным, а ID новый - 653 (т.е. это также новая точка монтирования, копия точки ID=414)

[NOTE]
====
Копия точки `shared` состоит в той же группе точек ID=216 (опциональное поле `shared:261`), что и исходная точка в родительском пространстве имён.
====

В первой консоли создадим по одной точке монтирования *непосредственно под* двумя точками:

414 30 0:56 / /tmp/mounts/shared rw,relatime shared:261 - tmpfs tmpfs rw,inode64
654 63 0:57 / /tmp/mounts/private/a rw,relatime - tmpfs tmpfs rw,inode64  <3>
656 414 0:65 / /tmp/mounts/shared/b rw,relatime shared:64 - tmpfs tmpfs rw,inode64  <4>

<1> Создаём точку монтирования `a` непосредственно под `private`
<2> Создаём точку монтирования `b` непосредственно под `shared`
<3> Точка `a` унаследовала тип родительской точки - `MS_PRIVATE`, её ID=654

===== MS_SLAVE

Создадим точку типа `MS_SHARED`. В первой консоли:

[source,console,options="nowrap"]
----
$ mkdir -p /tmp/mounts2/slave  <1>
$ sudo mount -t tmpfs tmpfs /tmp/mounts2/slave
$ sudo mount --make-shared /tmp/mounts2/slave  <2>

$ cat /proc/self/mountinfo | grep mounts2
433 30 0:67 / /tmp/mounts2/slave rw,relatime shared:714 - tmpfs tmpfs rw,inode64  <3>
----
<1> Создаём точку `slave` в исходном пространстве имён монтирования
<2> Изменяем тип точки `slave` на `MS_SHARED`
<3> Создана точка монтирования `/tmp/mount2/slave`: ID=433, тип `MS_SHARED`, состоит в группе точек монтирования ID=714 (опциональное поле `shared:714`)

Создаём новое пространство имён и изменяем тип клонированной точки на `MS_SLAVE`. В другой консоли:

[source,console,options="nowrap"]
----
$ sudo unshare -m --propagation unchanged /bin/bash  <1>
# export PS1="(mount ns) $PS1"

(mount ns) # cat /proc/self/mountinfo | grep mounts2
2390 2345 0:67 / /tmp/mounts2/slave rw,relatime shared:714 - tmpfs tmpfs rw,inode64  <2>

(mount ns) # mount --make-slave /tmp/mounts2/slave  <3>
(mount ns) # cat /proc/self/mountinfo | grep mounts2
2390 2345 0:67 / /tmp/mounts2/slave rw,relatime master:714 - tmpfs tmpfs rw,inode64  <4>
----
<1> Создаём новое пространство имён монтирования
<2> Точка `slave` клонирована как и ранее: ID=2390, тип `MS_SHARED`, состоит в группе ID=714

[#section-namespaces_pid]
=== Пространство имён PID (CLONE_NEWPID)

PID namespace изолирует пространство идентификаторов процессов{nbsp}<<Namespaces-lwn-part3>><<Namespaces-lwn-part4>><<Namespaces-toptal-intro>><<Namespaces-habr-intro>>. Каждый namespace имеет собственный PID 1.

Исторически в ядре Linux поддерживалось только одно дерево процессов. Дерево процессов представляет собой иерархическую структуру, подобную дереву каталогов файловой системы

С появлением механизма PID namespaces стала возможна поддержка нескольких деревьев процессов, полностью изолированных друг от друга.

В процессе загрузки ОС Linux:

* сначала создаётся процесс `init`, запускающий другие процессы и службы;
* в дереве процессов он является корневым, его идентификационный номер (PID) равен 1.

[NOTE]
====
Мы наблюдали (и даже модифицировали) эту процедуру запуска на примере сброса пароля, когда перезаписывали `init=/bin/bash`.
====

Механизм namespaces позволяет создавать отдельное ответвление дерева процессов с собственным PID 1. Процесс, который создаёт такое ответвление, являются частью основного дерева (namespace), но его дочерний процесс уже будет корневым в новом дереве.

Процессы в новом дереве никак не взаимодействуют с родительским процессом и даже не «видят» его. В то же время процессам в основном дереве доступны все процессы дочернего дерева. Наглядно это показано на следующей схеме:

.Пространство имён PID{nbsp}<<Namespaces-habr-intro>>
image::images/namespaces-pid.png[]

Можно создавать несколько вложенных пространств имён PID: один процесс запускает дочерний процесс в новом пространстве имён PID, a тот в свою очередь порождает новый процесс в новом пространстве и т.д.

Один и тот же процесс может иметь несколько идентификаторов PID (отдельный идентификатор в каждом пространстве имён - **см. пары идентификаторов на схеме**).

Пространство имён PID может быть создано только в момент порождения нового процесса с помощью link:{man-clone_2}[clone(2)] с флагом `CLONE_NEWPID`. Как только link:{man-clone_2}[clone(2)] вызывается с этим флагом, новый процесс немедленно оказывается в новом пространстве имён PID, в корне нового дерева процессов.

При уничтожении PID namespace процесс с PID 1 должен собрать все zombie-процессы.

.Пример: создание PID namespace в коде

Рассмотрим пример создания PID namespace в коде (файл `{example-pid_namespace_ex1}`).

[source,c,linenum,options="nowrap"]
----
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static char child_stack[1048576];

static int child_fn() {
    printf("[child]  Parent's PID in the new PID namespace: %ld\n", (long)getppid());
    printf("[child]  Child's PID in the new PID namespace:  %ld\n", (long)getpid());
    return 0;
}

int main() {
    printf("[parent] Parent's PID in the main PID namespace: %ld\n", (long)getpid());

    pid_t child_pid = clone(child_fn, child_stack+1048576, CLONE_NEWPID | SIGCHLD, NULL);
    printf("[parent] Child's PID in the main PID namespace:  %ld\n", (long)child_pid);

    waitpid(child_pid, NULL, 0);
    return 0;
}
----

Обратите внимание:

* в исходном (основном) пространстве имён PID namespace идентификаторы "обычные" - потомки `init`;
* в новом PID namespace PID дочернего == 1, т.е. он как бы подменяет `init`, причём в новом namespace у него нет родителя (PPID = 0).

Внесём в программу одно изменение и уберём флаг `CLONE_NEWPID` из вызова link:{man-clone_2}[clone(2)]:

----

Теперь link:{man-clone_2}[clone(2)] просто создаёт новый процесс - **почти** также, как link:{man-fork_2}[fork(2)]:

* link:{man-fork_2}[fork(2)] создаёт дочерний процесс, который представляет копию родительского, однако адресные пространства независимы;
* link:{man-clone_2}[clone(2)] не просто создаёт копию, но позволяет разделять элементы контекста выполнения между дочерним и родительским процессами;

[NOTE]
====
В приведённом выше примере с link:{man-clone_2}[clone(2)] используется аргумент `child_stack`, который задаёт положение стека для дочернего процесса. Так как дочерний и родительский процессы могут разделять адресное пространство, дочерний процесс не может выполняться на том же стеке, что и родительский. Поэтому родительский процесс должен установить пространство памяти для стека дочернего процесса и передать указатель на него в вызове link:{man-clone_2}[clone(2)].
====

.Пример: создание вложенных PID namespace

Рассмотрим пример создания вложенных PID namespace в коде (файл `{example-pid_namespace_ex2}`).

[source,c,linenum,options="nowrap"]
----
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static int delay = 60;
static char child_stack[1048576];
static char child_stack2[1048576];


static int child_fn2() {
    printf("[child 2] Child's PID in the second new PID namespace:      %ld\n", (long)getppid());
    printf("[child 2] Grandchild's PID in the second new PID namespace: %ld\n", (long)getpid());

    printf("[child 2] Sleeping for %d seconds...\n", delay);
    sleep(delay);
    printf("[child 2] Done\n");

    return 0;
}

static int child_fn() {
    printf("[child 1] Parent's PID in the new PID namespace:            %ld\n", (long)getppid());
    printf("[child 1] Child's PID in the new PID namespace:             %ld\n", (long)getpid());

    printf("[child 1] Spawning a grandchild process...\n");

    pid_t child_pid = clone(child_fn2, child_stack2+1048576, CLONE_NEWPID | SIGCHLD, NULL);
    printf("[child 1] Grandchild's PID in the new PID namespace:        %ld\n", (long)child_pid);

    waitpid(child_pid, NULL, 0);
    printf("[child 1] Done\n");

    return 0;
}

int main(int argc, const char* argv[]) {
    if (argc > 1) {
        delay = atoi(argv[1]);
    }

    printf("[parent]  Parent's PID in the main PID namespace:           %ld\n", (long)getpid());

    pid_t child_pid = clone(child_fn, child_stack+1048576, CLONE_NEWPID | SIGCHLD, NULL);
    printf("[parent]  Child's PID in the main PID namespace:            %ld\n", (long)child_pid);

    waitpid(child_pid, NULL, 0);
    printf("[parent]  Done\n");

    return 0;
}
----

=== Сетевое пространство имён (CLONE_NEWNET)

Network namespace предоставляет отдельный сетевой стек{nbsp}<<Namespaces-lwn-part7>><<Namespaces-toptal-intro>><<Namespaces-habr-intro>>:

* интерфейсы;
* IP-адреса;
* маршруты;
* firewall;
* пространство портов.

Благодаря пространству имён NET мы можем выделять для изолированных процессов собственные сетевые интерфейсы, даже loopback-интерфейс для каждого пространства имён будет отдельным.

[NOTE]
====
После создания Net namespace содержит только интерфейс loopback, причём в выключенном состоянии.
====

Сетевые пространства имён можно создавать с помощью:

* системного вызова link:{man-clone_2}[clone(2)] с флагом `CLONE_NEWNET`;
* системного вызова link:{man-unshare_2}[unshare(2)]: `unshare` позволяет процессу или потоку отделять части контекста исполнения, общие с другими процессами (потоками).

Помещения процессов в новое сетевое пространство имён возможно следующими способами:

* Процесс, создавший новое пространство имён, может порождать другие процессы, и каждый из этих процессов будет наследовать сетевое пространство имён родителя;
* В ядре имеется специальный системный вызов — link:{man-setns_2}[setns(2)], с его помощью можно поместить вызывающий процесс или поток в нужное пространство имён. Для этого требуется файловый дескриптор, который на это пространство имён ссылается. Он хранится в файле `/proc/<PID{nbsp}процесса>/ns/net`. Открыв этот файл, мы можем передать файловый дескриптор функции link:{man-setns_2}[setns(2)].
* При создании нового пространства имён с помощью команды ip создаётся файл в директории `/var/run/netns/`. Чтобы получить файловый дескриптор, достаточно просто открыть этот файл.

=== Пространство имён пользователей (User Namespace)

==== Виртуализация привилегий

Пространство имён пользователей изолирует *идентификаторы пользователей и групп* (UID/GID). User namespace позволяет процессам иметь один набор UID/GID внутри пространства имён и другой - снаружи, в родительском пространстве{nbsp}<<Namespaces-lwn-part5>><<Namespaces-lwn-part6>>.

В частности, пространства имён позволяют процессам иметь UID 0 (root) *внутри контейнера*, оставаясь непривилегированным пользователем на хосте. Это важнейшее, часто применяемое отображение позволяет выполнять привилегированные действия внутри изолированной среды, не влияя на систему в целом.

==== Создание пространств имён пользователей

Создание пространств имён пользователей выполняется с помощью вызова link:{man-clone_2}[clone(2)] или link:{man-unshare_2}[unshare(2)] с флагом `CLONE_NEWUSER`. Создание Net namespace не требует повышенных привилегий.

*Первый* процесс в новом пространстве получает полный набор capabilities внутри него. Повышенные привилегии позволяют первому процессу выполнять все необходимые инициализации в пространстве имен до того, как в нем будут созданы другие процессы.

[NOTE]
====
Первый вызов `exec()` приводит к сбросу всех capabilities.
 +
Как следствие, даже если при запуске процесса в пространстве имён пользователей выполняется настройка namespace и запуск программы с помощью `exec` - без создания нового процесса - capabilities всё равно сбрасываются, и вновь запущенная программа исполняется без повышенных привилегий.
====

При этом, хотя новый процесс имеет полный набор capabilities в новом пространстве имен пользователя, он не получает никаких capabilities в родительском пространстве имен, независимо от идентификаторов и capabilities процесса, вызывающего link:{man-clone_2}[clone(2)]. В частности, даже если root использует `clone(CLONE_NEWUSER)`, результирующий дочерний процесс не будет иметь capabilities в родительском пространстве имен.

==== Отображение UID/GID (UID/GID mapping)

Когда процесс попадает в пользовательское пространство имён, видимые ему идентификаторы пользователей и групп могут отличаться от идентификаторов тех же пользователей и групп в родительском пространстве. Например, процесс может быть запущен от UID 0 (root) внутри User namespace, но иметь UID 1000 (непривилегированный пользователь) вне этого пространства имён.

Чтобы такая схема работала корректно, ядру необходимо знать соответствие идентификаторов дочернего и родительского пространств имён. Это соответствие задаётся посредством механизма отображения UID/GID.

В новом пространстве имён по умолчанию сопоставление идентификаторов не задано, поэтому все UID/GID отображаются в значение overflow-ID, представляемое псевдофайлами `/proc/sys/kernel/overflowuid` и `/proc/sys/kernel/overflowgid`, соответственно (обычно overflow-ID=65534).

[NOTE]
====
Значения overflow-ID используются для всех UID/GID, для которых отображение не задано.
====

===== Механизм отображения: файлы uid_map и gid_map

При запуске процесса в `/proc` создаются два специальных файла:

* `/proc/<PID>/uid_map`;
* `/proc/<PID>/gid_map`.

Эти файлы определяют, как числовые идентификаторы внутри пространства имён преобразуются в идентификаторы родительского пространства. Изначально файлы пустые, т.к. по умолчанию сопоставление не задаётся.

Каждая строка в `uid_map` и `gid_map` имеет формат:
----
  ID-inside-ns   ID-outside-ns   length
----
где ID-inside-ns - начальный идентификатор внутри namespace, ID-outside-ns - соответствующий идентификатор в родительском пространстве, length - количество последовательных ID в диапазоне.

.Примеры

* `0 1000 1` означает сопоставление ID 0 внутри пространства имён с ID 1000 во родительском пространстве.
* `0 1000 5` означает сопоставление *пяти* ID [0, 4] внутри namespace с пятью ID [1000, 1004] в родительском пространстве.

[IMPORTANT]
====
При выполнении сопоставления ID-outside-ns всегда интерпретируется как ID в родительском пространстве имён.
====

===== Правила записи в uid_map и gid_map

Процесс, выполняющий запись в файлы отображений, должен иметь соответствующие capabilities:

* `CAP_SETUID` - для записи в `uid_map`;
* `CAP_SETGID` - для записи в `gid_map`;
* `CAP_DAC_OVERRIDE` - для открытия файлов.

[NOTE]
====
Технически, установка capabilities изменяет контекст безопасности процесса, что, помимо прочего, влечёт за собой монтирование файлов в `/proc/<PID>` с владельцем root:root.

Как следствие, непривилегированный процесс не может открыть файлы `uid_map` / `gid_map` - для обхода проверок DAC требуется `CAP_DAC_OVERRIDE`.
====

Процесс должен находиться либо в том же user namespace, что и целевой процесс, либо в родительском пространстве имён.

Записываемое отображение должно:

* либо состоять из одной строки, сопоставляющей только собственный эффективный UID/GID процесса-писателя;
* либо процесс должен иметь `CAP_SETUID` / `CAP_SETGID` в родительском пространстве имён, чтобы задавать произвольные диапазоны.

Как следствие этих правил, первый процесс в новом пользовательском пространстве имён не может сам задать произвольные сопоставления, так как у него нет привилегий в родительском пространстве. Для задания сложных или широких диапазонов отображений это должен сделать процесс из родительского namespace.

Ядро разрешает однократное выполнение записи в файлы `uid_map` и `gid_map` для каждого пространства имён. После того как сопоставление установлено, изменить его невозможно.
При этом сопоставление может быть задано несколькими строками, разделёнными `\n`, но должно быть записано одной операцией записи в файл.

С целью настройки возможности изменения групп (посредством системного вызова link:{man-setgroups_2}[setgroups(2)]) при создании процесса в `/proc` монтируется файл `/proc/<PID>>/setgroups`, содержимое которого определяет статус системного вызова:

* `allow` -	`setgroups()` разрешён;
* `deny` - `setgroups()` запрещён.

Задание отображений GID родительского и дочернего User namespace из *непривилегированного* процесса возможно только в случае запрета `setgroups()` в дочернем пространстве. Как следствие, запись в файл `/proc/<PID>/gid_map` должна предварять операция:
----
$ echo deny > /proc/<PID>>/setgroups
----

[WARNING]
====
Как показано в <<Namespaces-lwn-groups-dropping>><<Namespaces-lwn-loophole>>, сброс групп, интуитивно представляемый как операция, снижающая привилегии, на самом деле может приводить к повышению прав доступа.

Например, файл `file` доступен для владельца `user` и пользователей, не состоящих в группе `dev`:
----
$ ls -l file
-rwx---rwx 1 user dev 16448 Dec 31 23:59 file
----
Предположим, что некий процесс `proc` запущен от имени пользователя `user2` и содержит группу `dev` в списке групп процесса. Тогда проверки прав доступа выполняются по второму триплету, поэтому `proc` не может выполнять операции с `file`.
 +
Предположим далее, группа `dev` удаляется из списка групп процесса. Теперь проверки прав доступа выполняются по третьему триплету, что предоставляет полный доступ к `file`.

Подобный механизм ограничения доступа через группы действительно применяется на практике, поэтому операция сброса групп является потенциально опасной.
====

==== Ограничения механизма User namespace

* Не все файловые системы поддерживают User namespaces.
* Так как четвёрки идентификаторов UID/GID используются повсеместно в коде ядра, реализация механизма User namespaces крайне сложна; работы по исправлению многочисленных багов были завершены примерно ко времени появления версии 3.8. Однако вполне может быть, что какие-то ошибки всё ещё не найдены...
* Как и все новые механизмы, сопряжение со старыми конфигурациями системы может повлечь за собой неожиданные проблемы (наподобие обсуждённого ранее повышения привилегий через сброс групп).

static void setup_user_namespace(uid_t child_pid, int verbose) {
    char path[256], mapping[32];

    // получаем real UID и GID - эти ID необходимо отразить на 0 во вновь созданном User namespace
    uid_t real_uid = getuid();
    gid_t real_gid = getgid();

    if (verbose) {
        printf("[Parent]    UID=%jd GID=%jd;  capabilities: %s\n", (intmax_t) real_uid, (intmax_t) real_gid, cap_to_text(cap_get_proc(), NULL));

    // real UID <-> 0
    snprintf(path, sizeof(path), "/proc/%jd/uid_map", (intmax_t) child_pid);  <1>
    snprintf(mapping, sizeof(mapping), "0 %jd 1", (intmax_t) real_uid);
    write_file(path, mapping);

    if (verbose) {
        printf("[Parent]    Mapped real UID %jd <-> User ns 0\n", (intmax_t) real_uid);
    }

    // запрет `setgroups(2)` для защиты от сброса групп через User namespace (см. https://lwn.net/Articles/621612/)
    // необходимо для настройки отображения GID
    snprintf(path, sizeof(path), "/proc/%jd/setgroups", (intmax_t) child_pid);  <2>
    write_file(path, "deny");

    if (verbose) {
        printf("[Parent]    Switched off setgroups(2)\n");
    }

    // real GID <-> 0
    snprintf(path, sizeof(path), "/proc/%jd/gid_map", (intmax_t) child_pid);  <3>
    snprintf(mapping, sizeof(mapping), "0 %jd 1", (intmax_t) real_gid);
    write_file(path, mapping);

    if (verbose) {
        printf("[Parent]    Mapped real GID %jd <-> User ns 0\n", (intmax_t) real_gid);
    }
}
----
<1> Настраиваем отображение UID пользователя x (UID=1001) на root (UID=0): записываем `0 1001 1` в файл `/proc/<PID>/uid_map`
<2> Отключаем системный вызов `setgroups` для дальнейшей настройки отображения GID: записываем `deny` в файл `/proc/<PID>/setgroups`
<3> Настраиваем отображение GID пользователя x (GID=1001) на root (GID=0): записываем `0 1001 1` в файл `/proc/<PID>/gid_map`

. Настройка Mount namespace
+
[source,c,linenums,start=128,options="nowrap"]
----
static void setup_mount_namespace(void) {
    // 1. Изменяем тип всех точек монтирования нового пространства имён на "MS_PRIVATE" (для изоляции от хостовой FS)
    mount(NULL, "/", NULL, MS_REC | MS_PRIVATE, NULL);  <1>

    // 2. Монтируем корень контейнера ("/" -> "/container/root")
    // i. делаем новый корень точкой монтирования - это требуется для использования `pivot_root`
    mount(HOST_NEW_ROOT, HOST_NEW_ROOT, "bind", MS_BIND | MS_REC, NULL);

    // ii. создаём директорию для перемонтирования текущего корня (сейчас это корень хостовой FS)
    int err = mkdir(HOST_OLD_ROOT, 0777);
    if (err != 0 && errno != EEXIST) {
        perror("[Container] mkdir");
        exit(EXIT_FAILURE);
    }

    // iii. с помощью `pivot_root` перемонтируем корень FS на "/container/root"
    if (syscall(SYS_pivot_root, HOST_NEW_ROOT, HOST_OLD_ROOT) != 0) {  <2>
        perror("[Container] pivot_root");
        exit(EXIT_FAILURE);
    }

    if (chdir("/") != 0) {
        perror("[Container] chdir");
        exit(EXIT_FAILURE);
    }

    // 3. Отвязываем старый корень и удаляем временную директорию `oldroot`
    // N.B. Обратите внимание, теперь путь к нему не "/container/root/oldroot", а "/oldroot"
    umount2(CONT_OLD_ROOT, MNT_DETACH);
    rmdir(CONT_OLD_ROOT);

    // 4. Монтируем proc FS
    mount("proc", "/proc", "proc", 0, NULL);
}
----
<1> Изменяем тип точки монтирования корня `/` на `MS_PRIVATE` для полноценной изоляции дочернего пространства от родительского (основного) +
*N.B.* Операция выполняется в новом пространстве имён монтирования, точка монтирования `/` хостовой FS не изменяется.
<2> Монтируем директорию с Alpine Linux `/container/root` на корень FS `/` в новом Mount namespace

. Настройка Net namespace
+
Сетевой код использует библиотеку `libnl` для создания и настройки пары veth-интерфейсов, а также помещения одного из интерфейсов в новый Net namespace.
+
Функция `setup_veth_parent(child_pid)`:
+
  * создаёт пару veth-интерфейсов `veth-host` и `veth-cont`;
  * настраивает адрес 172.16.42.1/24 и запускает интерфейс `veth-host`;
  * переносит интерфейс `veth-cont` во вновь созданный Net namespace.
+
Функция `setup_veth_child(void)` (все операции выполняются в новом Net namespace):
+
  * запускает интерфейс `lo`;
  * переименовывает интерфейс `veth-cont` в `eth0`, настраивает адрес 172.16.42.2/24 и запускает `eth0`;
  * настраивает маршрут по умолчанию (default gateway) через 172.16.42.1.
+
*N.B.* Для огранизации доступа в Интернет из контейнера необходимо настроить source NAT между интерфейсом `veth-host`, на который будут приходить пакеты из контейнера, и физическим интерфейсом хоста (обычно `enp0s3`). В рамках настоящего примера это делается на хосте (см. следующий раздел).

. Настройка Seccomp
+
Для конфигурации правил seccomp используется библиотека `libseccomp`. В зависимости от запускаемого процесса устанавливается либо профиль "shell" (при запуске `/bin/sh`), позволяющий практически любые действия в системе, либо "restricted" (при запуске остальных исполняемых файлов), существенно ограничивающий возможности процессов:
+
[source,c,linenums,start=550,options="nowrap"]
----
void setup_seccomp(const char *programm, int verbose) {
    if (strcmp(programm, "/bin/sh") == 0) {
        if (verbose) {
            printf("[Container] Using shell seccomp profile\n");
        }
        install_shell_profile();  <1>
    } else {
        if (verbose) {
            printf("[Container] Using restricted seccomp profile\n");
        }
        install_restricted_profile();  <2>
    }
}
----
<1> Устанавливаем профиль "shell"
<2> Устанавливаем профиль "restricted"
+
Создание правил выполняется в соответствующих функциях, для "shell" - `install_shell_profile()`:
+
[source,c,linenums,start=522,options="nowrap"]
----
static void install_shell_profile(void) {
    /*
     *  Менее органичивающий профиль, позволяющий нормальное функционирование командного интерпретатора `/bin/sh`
     */
    scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_ALLOW);  <1>
    if (!ctx) {
        perror("seccomp_init");
        exit(EXIT_FAILURE);
    }

    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(clone), 0);  <2>
    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(clone3), 0);

    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(ptrace), 0);
    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(bpf), 0);
    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(kexec_load), 0);
    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(perf_event_open), 0);
    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(init_module), 0);
    seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(finit_module), 0);

    if (seccomp_load(ctx) < 0) {  <3>
        perror("seccomp_load (shell)");
        exit(EXIT_FAILURE);
    }

    seccomp_release(ctx);
}
----
<1> Устанавливаем действие по умолчанию: разрешение системного вызова (действие `SCMP_ACT_ALLOW`)
<2> Добавляем правила, запрещающее исполнение ряда системных вызовов (действие `SCMP_ACT_KILL`): `clone`, `clone3`, `ptrace` и др.
<3> Загружаем сформированный набор правил
+
Профиль "restricted" конфигурируется в функции `install_restricted_profile()` аналогичным образом.

Также в текущем виде код `{example-container}` организован так, что запретить системный вызов `execve()` средствами seccomp не представляется возможным без модификации запускаемого в контейнере приложения. Среди возможных способов реализации контроля за исполнением `execve()`:

* создание специального профиля link:{info-apparmor}[AppArmor] / link:{man-selinux_8}[SELinux(8)];
* создание белого списка доступных для запуска с помощью `execve()` программ посредством механизма link:{man-landlock_7}[Landlock(7)];
* кастомный фильтр link:{info-ebpf}[eBPF], выполняющий динамическую фильтрацию системных вызовов.

Оставляем реализацию описанных выше улучшений читателю в качестве упражнения. Да прибудет с вами сила!
